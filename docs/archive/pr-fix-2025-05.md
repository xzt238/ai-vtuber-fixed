### 🔴 BUG-1：`set_progress()` 方法定义两次

**文件**: `native/gugu_native/widgets/splash_debug_window.py`

**问题分析**:
- 行 320：第一个 `set_progress()` — 包含 `QApplication.processEvents()` 强制刷新 UI + `_center_on_screen()` 窗口居中
- 行 388：第二个 `set_progress()` — 覆盖了第一个，仅更新文字和 10 秒后显示跳过按钮
- Python 中后定义的方法覆盖前者，导致：
  - 进度更新时 UI 不会强制刷新（`processEvents()` 丢失）
  - 窗口不会在进度更新时居中（`_center_on_screen()` 丢失）
  - 启动画面进度显示卡顿

**修复方案**: 合并两个方法为一个，保留两段所有功能：

```python
def set_progress(self, text: str):
    """更新启动进度文字 — 供 main.py 各阶段调用"""
    self._progress_label.setText(text)
    QApplication.processEvents()       # 立即刷新 UI
    self._center_on_screen()           # 窗口居中

    # 首次调用 set_progress 后启动 10 秒倒计时显示跳过按钮
    if not hasattr(self, '_skip_timer_started'):
        self._skip_timer_started = True
        QTimer.singleShot(10000, self._show_skip_button)
```

**影响范围**: 仅 `splash_debug_window.py` 一个文件，不影响其他模块。

**验收标准**:
- [ ] 文件中 `set_progress` 方法定义唯一（仅出现一次 `def set_progress`）
- [ ] 合并后的方法同时包含 `QApplication.processEvents()`、`_center_on_screen()` 和跳过按钮计时器逻辑
- [ ] 启动画面进度更新时 UI 立即刷新，无卡顿
- [ ] 启动画面窗口始终居中显示

### 🟡 ARCH-1：VisionWorker 破坏封装，直接访问 VisionManager 私有属性

**文件**:
- `native/gugu_native/workers/vision_workers.py` — 行 29/34/37/73/80/83
- `app/vision/__init__.py` — VisionManager 类

**问题分析**:

当前 Worker 中的私有属性访问：

| 行号 | 代码 | 问题 |
|------|------|------|
| 29 | `vision._current_provider is None` | 检查 Provider 是否已配置 |
| 34 | `hasattr(vision, '_providers')` | 检查内部字典是否存在 |
| 37 | `vision._providers.get(VisionProviderType.RAPIDOCR)` | 直接获取特定 Provider 实例 |
| 73 | `vision._current_provider is None` | 同行 29 |
| 80 | `hasattr(vision, '_providers')` | 同行 34 |
| 83 | `vision._providers.get(VisionProviderType.RAPIDOCR)` | 同行 37 |

风险：如果 VisionManager 内部重构（例如删除 `_providers` 字典改用列表、或 MiMo Vision 的独立实例逻辑变更），所有 Worker 都会崩溃。

**修复方案**:

1. 在 `VisionManager`（`app/vision/__init__.py`）中添加公开接口：

```python
# ---- VisionManager 新增公开属性/方法 ----

@property
def current_provider(self) -> Optional[VisionProvider]:
    """当前活跃的 Provider 实例（只读）"""
    return self._current_provider

@property
def has_provider(self) -> bool:
    """是否已配置任意 Provider"""
    return self._current_provider is not None

def get_provider(self, provider_type: VisionProviderType) -> Optional[VisionProvider]:
    """
    按类型获取 Provider 实例

    Args:
        provider_type: Provider 类型枚举

    Returns:
        Provider 实例，不存在则返回 None
    """
    # 先查标准字典
    provider = self._providers.get(provider_type)
    if provider:
        return provider
    # 再查 MiMo（它使用 MINIMAX_VL 类型但独立存储）
    if provider_type == VisionProviderType.MINIMAX_VL:
        if hasattr(self, '_mimo_vision_provider') and self._mimo_vision_provider.is_available():
            return self._mimo_vision_provider
    return None
```

2. 修改 `vision_workers.py` 中 `OCRWorker.run()` 和 `VisionWorker.run()`，改用公开接口：

```python
# 修改前:
if vision is None or vision._current_provider is None:
    ...
if not text and hasattr(vision, '_providers'):
    rapidocr = vision._providers.get(VisionProviderType.RAPIDOCR)

# 修改后:
if vision is None or not vision.has_provider:
    ...
if not text:
    rapidocr = vision.get_provider(VisionProviderType.RAPIDOCR)
```

**影响范围**: `app/vision/__init__.py`（添加公开接口）+ `native/gugu_native/workers/vision_workers.py`（改用公开接口）。

**验收标准**:
- [ ] VisionManager 新增 `current_provider` property（只读）
- [ ] VisionManager 新增 `has_provider` property
- [ ] VisionManager 新增 `get_provider(type)` 方法
- [ ] `vision_workers.py` 中不再出现 `_current_provider` 和 `_providers` 的直接访问
- [ ] OCRWorker 和 VisionWorker 功能不受影响（回归测试通过）

### 🟡 ARCH-2：StreamChatWorker 和 LLM 内部双记忆检索

**文件**:
- `native/gugu_native/workers/chat_workers.py` — 行 78-87
- `app/llm/__init__.py` — `MemoryRAGInjector` 在 `build_messages()` 中

**问题分析**:

| 位置 | 检索方式 | 拼接方式 | 功能完整度 |
|------|----------|----------|------------|
| Worker 层（行 78） | `backend.memory.search(text, top_k=3)` | `"用户问题: {text}\n\n相关记忆:\n..."` 前缀拼接到 prompt | 简单拼接，无优先级/截断保护 |
| LLM 层（MemoryRAGInjector） | 内部检索 | 追加到 system prompt 末尾 | 区分工作记忆/情景记忆，有截断保护、优先级控制 |

同一次请求中记忆被检索两次的后果：
- **Token 浪费**：相同/相似的记忆片段被注入两次
- **信息重复**：LLM 可能过度关注重复出现的记忆片段
- **逻辑不一致**：两条路径的记忆选取逻辑不同（Worker 用 `top_k=3`，LLM 用自己的策略）

**修复方案**: 删除 Worker 层的记忆检索，统一由 LLM 内部的 `MemoryRAGInjector` 处理。

```python
# 修改前 (chat_workers.py 行 76-87):
def run(self):
    try:
        relevant_memories = self.backend.memory.search(self.text, top_k=3)
        context = ""
        if relevant_memories:
            context = "\n\n相关记忆:\n" + "\n".join(
                [m.get("content") or m.get("text", "") for m in relevant_memories]
            )

        full_prompt = self.text
        if context:
            full_prompt = f"用户问题: {self.text}{context}"
        ...

# 修改后:
def run(self):
    try:
        full_prompt = self.text  # 记忆由 LLM 内部 MemoryRAGInjector 统一处理
        ...
```

**影响范围**: 仅 `native/gugu_native/workers/chat_workers.py`，删除约 8 行代码。

**验收标准**:
- [ ] `chat_workers.py` 的 `StreamChatWorker.run()` 中不再调用 `backend.memory.search()`
- [ ] 对话功能正常：LLM 仍能检索和使用记忆（由 MemoryRAGInjector 处理）
- [ ] 不出现记忆重复注入的情况
- [ ] 记忆相关场景回归测试通过（如：提及过去的对话内容，LLM 能正确回忆）

### 🟡 ARCH-3：LLM 请求失败后立即重试，无退避

**文件**: `native/gugu_native/workers/chat_workers.py` — 行 112-121

**问题分析**:

```python
# 当前代码:
if not reply and not stream_error:
    result = self.backend.llm.stream_chat(...)  # 立即重试，无延迟
```

如果服务端限流（429）或临时过载，连续两次无间隔请求会：
- 第二次请求同样失败
- 可能加剧服务端压力
- 浪费网络资源和等待时间

**修复方案**: 添加重试前短暂延迟 + 最大重试次数限制：

```python
# 修改后:
MAX_RETRIES = 1        # 最多重试 1 次
RETRY_DELAY_SEC = 2    # 重试前等待 2 秒

# ... 在 run() 方法中:

if not reply and not stream_error:
    if not hasattr(self, '_retry_count'):
        self._retry_count = 0
    if self._retry_count < MAX_RETRIES:
        self._retry_count += 1
        import time
        time.sleep(RETRY_DELAY_SEC)
        result = self.backend.llm.stream_chat(
            full_prompt,
            list(self.history),
            callback=on_chunk,
            on_tool_call=on_tool_call
        )
        reply = result.get("text", "")
        action = result.get("action")
        stream_error = result.get("_stream_error")
```

> 注：此为简单退避方案。如需更健壮的重试策略，建议复用 `app/llm/__init__.py` 中已有的 `RetryStrategy`（指数退避重试）类。

**影响范围**: 仅 `native/gugu_native/workers/chat_workers.py`。

**验收标准**:
- [ ] 重试前有 2 秒延迟
- [ ] 最多重试 1 次（不无限重试）
- [ ] 停止请求（`stop_stream`）时仍能及时退出
- [ ] 限流场景下第二次请求成功率提升
